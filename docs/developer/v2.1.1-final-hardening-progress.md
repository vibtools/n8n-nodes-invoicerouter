## Phase 01 verified contract

After every retry or failover Wait, the canonical workflow rereads `provider`, reruns Provider Loader, rebuilds the process-local provider pool and secret vault, restores the waited job, and re-enters Provider Selector. Same-account lifecycle retry preserves `requiredProfileId`; pre-side-effect failover clears it while preserving attempted-profile exclusion.

## Phase 02 verified contract

Startup now reads `email_list`, `retry_queue`, `invoice_results`, `campaign_report`, and `account_report`. `Build Durable Work Items` reconstructs the selected campaign's admitted jobs, terminal jobs, counters, pause state, last-attempt timestamp, lease metadata, and revision from Sheet evidence. Workflow static data and process memory remain caches, not the campaign correctness source.

The canonical Odoo workflow enforces:

```text
one execution = one pending Campaign_ID
-> prepare campaign lease
-> campaign_report append/update
-> campaign_report reread
-> verify Run_ID + ACTIVE state + Revision + expiry
-> one-item provider loop
-> release lease after loop completion
```

Additive `campaign_report` columns:

```text
Run_State
Run_ID
Lock_Acquired_At
Lock_Expires_At
Revision
Last_Attempt_At
```

An active unexpired lease owned by another execution blocks before provider selection. The lease is reread after acquisition to reduce overlapping-run races. Google Sheets is not transactional, so operators must still avoid launching the same `Campaign_ID` concurrently.

The existing eight exported custom node types remain unchanged. Phase 02 adds only built-in Google Sheets/Code nodes and additive Sheet columns.

## Phase 03 verified contract

Odoo email truth is now derived in this precedence order:

```text
current-attempt intended-recipient SENT evidence
-> current-attempt intended-recipient QUEUED evidence
-> explicit notification/mail failure evidence
-> ambiguous wizard transport without terminal evidence = UNVERIFIED
-> definitive wizard/setup failure = FAILED
```

The non-throwing Odoo probes preserve structured `OdooOperationError` metadata in `emailEvidence.wizardErrorDetails`, including model, method, lifecycle stage, ambiguity, and side-effect classification. A timeout from `account.move.send.wizard.action_send_and_print` therefore does not erase later provider evidence and does not become an unsafe automatic retry.

Partner resolution uses `=ilike`, reads at most two candidate contacts, normalizes exact email addresses, and blocks duplicate or non-exact matches before invoice creation. Recipient evidence recognizes RFC display-name forms. PDF evidence independently reads `ir.attachment` and validates `application/pdf`, `account.move`, the current invoice ID, current-attempt message binding, and the invoice's `invoice_pdf_report_id`.

The frozen eight custom nodes, workflow topology, Sheet schema, package APIs, libraries, and provider-selection behavior remain unchanged in Phase 03.


## Phase 04 implemented contract

One shared manifest defines the Odoo surface consumed by preflight, sender, and tests. Odoo 18 and 19 retain documented wizard metadata; unprofiled versions use the common capability profile and are not blocked by version number alone. Preflight validates all declared model fields, performs read probes, reads the authenticated user's company, and records `Odoo_Server_Version`, `Odoo_Major_Version`, and `Capability_Status`.

The capability result is intentionally `CAPABILITY_VALIDATED_SIDE_EFFECT_PERMISSION_UNPROVEN`: read-only preflight cannot prove create/post/send permission. A controlled canary remains mandatory.

Every enabled Odoo profile must provide `Issuer_Key`. Accounts in one `Failover_Group` must share a normalized issuer key and the same preflight-resolved company identity. A mismatch removes the whole group from the runtime pool and reports `ISSUER_MISMATCH` without permanently toggling the source row's `Enabled` field.

The eight custom nodes, package APIs, and dependencies remain frozen. Phase 04's verified workflow baseline was 114 nodes and 129 edges.

## Phase 06 — implemented

Campaign and account report rows now carry `Base_Revision`, `Revision`, `Writer_Run_ID`, and `Aggregate_Source`. The canonical workflow rereads the target report immediately before each main report write and rejects a candidate unless:

```text
current Revision = candidate Base_Revision
candidate Revision = Base_Revision + 1
campaign Writer_Run_ID = active campaign Run_ID
```

Pending writeback repair applies the same revision contract. Already-applied or older report payloads are skipped as stale; revision gaps fail closed instead of overwriting newer Sheet state.

Campaign counters are rebuilt from durable `email_list`, `invoice_results`, and `retry_queue` evidence at startup rather than taking the maximum of a prior aggregate row. Account aggregates restart from the highest-revision `account_report` row and advance once per runtime event. Odoo preflight issuer mismatches are written as revisioned `PREFLIGHT` account-report rows with issuer and company evidence.

The canonical and URL-import workflows remain byte-identical at 132 built-in/custom nodes and 148 edges after the final corrective audit. The eight exported InvoiceRouter custom nodes remain unchanged.
