# Logs

Welcome to the **InvoiceRouter** logging directory.

The **logs/** directory stores runtime logs generated by the application, development tools, automation scripts, and diagnostic utilities.

Logs are intended for monitoring, troubleshooting, debugging, and auditing project activity.

---

# Purpose

The logging system exists to:

* Record application events.
* Capture execution details.
* Assist with debugging.
* Support troubleshooting.
* Improve operational visibility.
* Provide diagnostic information.

Logs should help developers understand what happened without affecting application behavior.

---

# Directory Structure

```text
logs/

README.md

application/

build/
debug/

tests/
```

Subdirectories may expand as the project grows.

---

# Log Categories

## application/

Application runtime logs.

Examples:

* Node execution
* Provider execution
* Runtime events
* System information

---

## automation/

Automation script logs.

Examples:

* Build automation
* Validation
* Auto-fix
* Release
* Publish

---

## build/

Build process logs.

Examples:

* Compilation output
* Build summary
* Warnings
* Errors

---

## debug/

Debug information generated during development.

Examples:

* Variable dumps
* Diagnostic output
* Performance traces

Debug logs should never be required for production.

---

## errors/

Unexpected errors and exception reports.

Examples:

* Stack traces
* Fatal errors
* Validation failures
* Runtime exceptions

Sensitive information should never be written to error logs.

---

## tests/

Test execution logs.

Examples:

* Test summaries
* Failed assertions
* Coverage reports
* Integration results

---

# Logging Principles

Logs should be:

* Informative
* Consistent
* Readable
* Structured
* Timestamped
* Easy to search

Avoid unnecessary or repetitive log entries.

---

# Sensitive Information

Logs must never contain:

* API Keys
* Access Tokens
* Passwords
* Secrets
* Private Keys
* Customer credentials
* Personally identifiable information (PII)

Sensitive values should always be masked or omitted.

---

# Log Levels

Recommended log levels:

| Level | Purpose                                |
| ----- | -------------------------------------- |
| DEBUG | Development diagnostics                |
| INFO  | Normal application events              |
| WARN  | Recoverable issues                     |
| ERROR | Failures requiring attention           |
| FATAL | Critical failures preventing execution |

Choose the lowest appropriate level for each event.

---

# File Naming

Use descriptive file names.

Examples:

```text
application.log

build.log

release.log

validation.log

error.log
```

Avoid generic names such as:

```text
log.txt

output.txt

test.txt

temp.log
```

---

# Rotation and Cleanup

Log files may grow over time.

Recommended practices:

* Rotate large log files.
* Archive historical logs when necessary.
* Remove obsolete logs during cleanup.
* Keep only the required retention period.

Automation may periodically clean old log files.

---

# Git Policy

Runtime logs should **not** be committed to the repository.

Only the following files should normally exist in Git:

* README.md
* `.gitkeep` (optional)

All generated log files should be ignored using `.gitignore`.

Example:

```gitignore
logs/*
!logs/README.md
!logs/.gitkeep
```

---

# Architecture Compliance

The **logs/** directory is not part of the runtime architecture.

Application code should write logs here but must not depend on existing log files for correct operation.

Deleting log files must never affect application behavior.

---

# Contribution Guidelines

When introducing new logging:

* Log meaningful events only.
* Avoid duplicate entries.
* Use consistent formatting.
* Never expose sensitive information.
* Update documentation if new log categories are introduced.
